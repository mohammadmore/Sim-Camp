# Sim-Camp — سامانه امتیازدهی زنده سیمولیشن کمپ

پنل سوپرادمین (ساخت مسابقه)، پنل اپراتور/سرداور/داور (ثبت امتیاز) و تابلوی زنده نتایج.

دو نسخه‌ی بک‌اند با رفتار یکسان وجود دارد:

| نسخه | مسیر | دیتابیس |
|---|---|---|
| Node.js | `server.js` + `public/` | Firebase Firestore (یا `memory` برای تست) |
| PHP (سی‌پنل) | `cpanel_export/` | SQLite خودکار یا MySQL — راهنما: [`cpanel_export/README.md`](cpanel_export/README.md) |

## اجرای نسخه Node

```bash
npm install
cp .env.example .env   # و مقادیر را تنظیم کنید
SUPERADMIN_PASS='یک-رمز-قوی' FIREBASE_SERVICE_ACCOUNT="$(cat service-account.json)" npm start
```

- **رمز سوپرادمین:** از `SUPERADMIN_PASS` خوانده می‌شود. اگر تنظیم نشده باشد، یک رمز تصادفی ساخته و یک‌بار در لاگ سرور چاپ می‌شود.
  وقتی رمز از داخل پنل (تنظیمات) عوض شود، رمز پنل بر متغیر محیطی مقدم است؛ برای بازیابی رمز فراموش‌شده سرور را یک‌بار با `SUPERADMIN_PASS_RESET=1` اجرا کنید.
- **Firebase:** فایل `firestore.rules` همه‌ی دسترسی‌های مستقیم را می‌بندد؛ سرور با **Firebase Admin SDK** کار می‌کند و به یک Service Account نیاز دارد
  (Firebase Console ← Project settings ← Service accounts ← Generate new private key). محتوای JSON را در `FIREBASE_SERVICE_ACCOUNT` قرار دهید
  یا مسیر فایل را در `GOOGLE_APPLICATION_CREDENTIALS`. سپس rules را منتشر کنید: `firebase deploy --only firestore:rules`.
  بدون Service Account سرور با هشدار به SDK وب برمی‌گردد که فقط با rules باز کار می‌کند (ناامن).
- **تست محلی بدون Firebase:** `DB_ADAPTER=memory SUPERADMIN_PASS=test npm start`

## توسعه

```bash
npm test               # تست‌های API روی هر دو بک‌اند (Node و PHP، در صورت نصب بودن php)
npm run build:cpanel   # ساخت cpanel_export/ از روی public/
```

فرانت‌اند فقط در `public/` ویرایش شود؛ `cpanel_export/*.html` و فایل‌های استاتیک آن خروجی build هستند.

## امنیت و نقش‌ها

- ورود سوپرادمین و کاربران مسابقه یک توکن نشست امضاشده (۱۲ ساعته) می‌دهد که در هدر `X-Auth-Token` ارسال می‌شود؛ رمز عبور در مرورگر ذخیره نمی‌شود.
- رمزها به صورت هش ذخیره می‌شوند (رمزهای متنی قدیمی در اولین ورود موفق هش می‌شوند). تغییر رمز یک کاربر نشست‌های فعلی او را باطل می‌کند.
- **داور:** ثبت امتیاز لحظه‌ای، نمره مرحله با نام خودش، لغو امتیازهای خودش.
- **اپراتور / سرداور:** موارد بالا + تنظیمات مسابقه، اصلاح دستی نمرات و تاریخچه، حذف نمره داوران، بستن/بازگشایی مراحل پلکانی.
- تابلوی زنده و صفحه‌ی ورود فقط داده‌ی عمومی (بدون رمز و فهرست کاربران) دریافت می‌کنند.

## صفحه‌ها

| صفحه | کاربر |
|---|---|
| `superadmin.html` | ساخت، ویرایش، تکثیر، آرشیو و حذف مسابقه (سطل زباله ۳۰ روزه)؛ پشتیبان‌گیری و بازیابی؛ لینک و QR؛ تغییر رمز سوپرادمین |
| `operator.html?id=…` | اپراتور، سرداور و داور (داوری میدانی و مراحل، کرنومتر، مدیریت مسابقه، اعلام نتایج) |
| `board.html?id=…` | تابلوی زنده (تمام‌صفحه با کلید F، مرحله جاری، سکوی نتایج نهایی) |
| `results.html?id=…` | جدول نتایج و تقدیرنامه‌ها برای چاپ یا ذخیره PDF |
| `team.html?id=…&team=…` | صفحه اختصاصی هر تیم (رتبه، بازیکن‌ها، مهارت‌ها، تاریخچه؛ با کد تیم: انتخاب تاکتیک، کارت محرمانه، رأی هم‌تیمی) |
| `live.html?id=…` | جدول سبک برای گوشی تماشاچی‌ها |
| `widget.html?id=…&n=5` | ویجت جدول برای قرار دادن در سایت (iframe) |
| `register.html?id=…` | فرم ثبت‌نام آنلاین تیم‌ها |
| `analysis.html?id=…` | اتاق آنالیز، کارنامه‌ها، آمار و خروجی اکسل (اپراتور/سرداور، سوپرادمین یا لینک گزارش مشتری) |
| `league.html?id=…` | جدول لیگ (جمع چند مسابقه) |

اپ قابل نصب (PWA) است و در صورت قطع اینترنت، امتیازهای داوران در صف می‌مانند و پس از اتصال خودکار ارسال می‌شوند.
نصب و کار آفلاین فقط روی HTTPS (یا localhost) فعال می‌شود.

## پایداری و پایش

- **سلامت سرور:** `GET /health` (نسخه PHP: `api.php?action=health`) وضعیت سرور و پایگاه داده را برمی‌گرداند؛ در صورت مشکل کد ۵۰۳ می‌دهد.
  آن را در یک سرویس پایش (مثلاً UptimeRobot) هر ۱ تا ۵ دقیقه بررسی کنید تا هنگام قطعی هشدار بگیرید.
- **اجرای پایدار Node:** با pm2 اجرا کنید تا پس از خطا یا مصرف زیاد حافظه خودکار ری‌استارت شود:
  `npm i -g pm2 && pm2 start ecosystem.config.cjs && pm2 save && pm2 startup`.
  برای بار بیشتر می‌توان چند نسخه اجرا کرد (بخش «چند نسخه از سرور» را ببینید).
- اگر هنگام شروع پایگاه داده در دسترس نباشد، سرور بالا می‌آید و مدام دوباره تلاش می‌کند (تا آن زمان API پاسخ «در حال راه‌اندازی» می‌دهد).
  خطاهای تنظیمات (مثل `FIREBASE_SERVICE_ACCOUNT` نامعتبر) همان ابتدا با پیام واضح گزارش می‌شوند.
- **محدودیت‌ها:** زمان هر عملیات دیتابیس و هر قفل محدود است؛ حجم درخواست (۲۵۶ کیلوبایت، و ۱۰ مگابایت فقط برای فرم‌های دارای عکس پس از ورود)،
  تعداد درخواست هر IP و تعداد تابلوهای زنده محدود شده‌اند. مقادیر در `.env.example` قابل تغییرند.
  در نسخه PHP محدودیت نرخ درخواست فقط وقتی APCu روی هاست فعال است کار می‌کند؛ در غیر این صورت از فایروال هاست یا Cloudflare استفاده کنید.
- **پشت پروکسی:** اگر سرور مستقیماً و بدون پروکسی در اینترنت است `TRUST_PROXY=0` بگذارید.

## ساختار داده و کارایی (نسخه Node)

- **کش در حافظه:** هر مسابقه‌ی در حال استفاده در حافظه‌ی سرور نگه داشته می‌شود؛ poll، تابلوی زنده و ورود دیگر از پایگاه داده نمی‌خوانند
  و پاسخ عمومی (JSON) فقط یک‌بار بعد از هر تغییر ساخته می‌شود. مسابقه‌ای که ۱۰ دقیقه استفاده نشود از حافظه خارج می‌شود (`CACHE_IDLE_MINUTES`).
- **پاسخ «بدون تغییر»:** `api?action=poll` هدر `ETag` دارد؛ اگر داده عوض نشده باشد پاسخ `304` بدون بدنه برمی‌گردد (در هر دو نسخه).
  پنل اپراتور و تابلوی نسخه PHP در این حالت صفحه را دوباره رسم نمی‌کنند.
- **عکس‌ها جدا از داده‌ها:** عکس تیم‌ها، لوگوها و عکس پروفایل یک‌بار ذخیره می‌شوند (نام فایل = هش محتوا) و با آدرس `/media/…`
  (نسخه PHP: `media.php?f=…`) و کش یک‌ساله سرو می‌شوند؛ دیگر داخل هر poll و هر به‌روزرسانی تابلو تکرار نمی‌شوند.
  در Firebase عکس‌ها در **Firebase Storage** (`media/…`) ذخیره می‌شوند؛ اگر Storage فعال نباشد خودکار در مجموعه‌ی `media` در Firestore.
  باکت از `storageBucket` فایل `firebase-applet-config.json` یا `FIREBASE_STORAGE_BUCKET` خوانده می‌شود؛ `MEDIA_BACKEND=firestore` استفاده از Storage را خاموش می‌کند.
  فایل `storage.rules` هم دسترسی مستقیم را می‌بندد: `firebase deploy --only firestore:rules,storage`.
- **امتیازها در مجموعه‌ی جدا:** هر امتیاز لحظه‌ای یک سند در `camps/{id}/logs` است؛ ثبت امتیاز سند مسابقه را بازنویسی نمی‌کند،
  بنابراین سقف ۱ مگابایتی سند Firestore با زیاد شدن امتیازها پر نمی‌شود و امتیازهای هم‌زمان با هم تداخل ندارند.
- **مهاجرت خودکار:** مسابقه‌هایی که با نسخه‌ی قبلی ذخیره شده‌اند (امتیاز و عکس داخل سند) در اولین استفاده خودکار به ساختار جدید منتقل می‌شوند.

## چند نسخه از سرور

نسخه Node را می‌توان هم‌زمان در چند پردازه یا چند ماشین روی **یک** پروژه‌ی Firebase اجرا کرد (مثلاً Cloud Run با چند instance یا pm2 در حالت cluster):

- هر نسخه تغییرات بقیه را از طریق listenerهای Firestore بلافاصله دریافت می‌کند؛ کش، تابلوهای زنده (SSE) و انیمیشن امتیاز روی همه‌ی نسخه‌ها به‌روز می‌مانند.
- نوشتن روی سند مسابقه با شماره‌ی نسخه (`rev`) و تراکنش انجام می‌شود؛ اگر دو نسخه هم‌زمان یک مسابقه را تغییر دهند، دومی خودکار دوباره روی داده‌ی تازه اجرا می‌شود و تغییری گم نمی‌شود.
- کلید نشست و رمز سوپرادمین بین نسخه‌ها مشترک است (تغییر رمز در یک نسخه در بقیه هم اعمال می‌شود). بهتر است `SESSION_SECRET` و `SUPERADMIN_PASS` را برای همه یکسان تنظیم کنید.
- محدودیت نرخ درخواست و ورود ناموفق برای هر نسخه جداگانه شمرده می‌شود.
- در pm2: در `ecosystem.config.cjs` مقدار `instances` را بیشتر کنید و `exec_mode: 'cluster'` بگذارید. حالت `DB_ADAPTER=memory` فقط برای یک نسخه است.
- تست: `FIRESTORE_EMULATOR_HOST=127.0.0.1:8089 npm test` دو سرور را روی Firestore Emulator اجرا و هماهنگی آن‌ها را بررسی می‌کند.

## پشتیبان‌گیری و بازیابی

- **حذف نرم (سطل زباله):** «حذف» مسابقه را به سطل زباله می‌برد؛ لینک‌ها و تابلو بلافاصله از کار می‌افتند ولی تا ۳۰ روز (`TRASH_DAYS`)
  از دکمه‌ی «سطل زباله» قابل بازگرداندن است. بعد از آن (یا با «حذف دائمی») برای همیشه پاک می‌شود.
- **فایل پشتیبان از پنل:** دکمه‌ی «خروجی» روی هر مسابقه، یا «پشتیبان‌گیری ← دانلود پشتیبان کامل» یک فایل JSON شامل مسابقه‌ها، امتیازها، کاربران و عکس‌ها می‌دهد.
  با «بازیابی از فایل پشتیبان» در **هر دو نسخه** (Node و cPanel) برمی‌گردد. بازیابی هیچ مسابقه‌ای را بازنویسی نمی‌کند؛ اگر لینک تکراری باشد لینک جدید می‌گیرد.
  رمزهای عبور بین دو نسخه قابل انتقال نیستند (فرمت هش متفاوت است)؛ پس از انتقال، از «ویرایش» رمز جدید تعیین کنید.
- **پشتیبان خودکار نسخه Node:** `node scripts/backup.mjs [پوشه] [تعداد]` (پیش‌فرض `./backups` و نگه‌داشتن ۱۴ فایل آخر). مثلاً با cron هر شب ساعت ۳:

  ```cron
  0 3 * * * cd /srv/sim-camp && /usr/bin/node scripts/backup.mjs /var/backups/sim-camp 30 >> /var/log/sim-camp-backup.log 2>&1
  ```

  فایل‌های پشتیبان را در جای دیگری (مثلاً یک باکت یا سرور دیگر) هم کپی کنید.
- **پشتیبان خود Firestore:** علاوه بر موارد بالا، پشتیبان‌گیری زمان‌بندی‌شده‌ی Google را فعال کنید:

  ```bash
  gcloud firestore backups schedules create --database='(default)' --recurrence=daily --retention=14d
  # یا خروجی دستی/زمان‌بندی‌شده در یک باکت:
  gcloud firestore export gs://YOUR_BUCKET/firestore-backups
  ```

  (اگر از دیتابیس نام‌دار استفاده می‌کنید، نام آن را از `firestoreDatabaseId` در `firebase-applet-config.json` بگذارید.)
- **نسخه cPanel:** راهنمای cron در [`cpanel_export/README.md`](cpanel_export/README.md) (اسکریپت `backup.php`).

## امکانات اختیاری و تنظیمات نمایش

اصل کار: **هر المان نمایشی به‌طور پیش‌فرض نمایش داده می‌شود** و برای هر مسابقه یک کلید «عدم نمایش» دارد؛
**امکاناتی که از داور ورودی بیشتری می‌خواهند تا روشن نشوند هیچ چیزی به صفحه داور اضافه نمی‌کنند.**

- **کجا تنظیم می‌شود:** اپراتور/سرداور در «مدیریت مسابقه ← تنظیمات پیشرفته»، سوپرادمین در پایین فرم مسابقه («امکانات پیشرفته، نمایش و برند»).
  پیش‌فرض نمایش برای مسابقه‌های جدید در «تنظیمات» سوپرادمین (با دو پیش‌تنظیم «جشنواره‌ای» و «رسمی»).
- **صفحه داور (فقط ساده‌کننده‌ها):** تیم‌ها و مراحل سپرده‌شده به هر داور، تایمر، یادآور «تیم‌های مانده»، پیام اپراتور،
  یادداشت و عکس با نگه داشتن دکمه «ثبت»، و فقط اگر روشن شوند: انتخاب بازیکن، داوری چندمعیاره، کارگاه هماهنگی، ثبت اعتراض.
- **میز کنترل اپراتور:** تایمر، نوار خبری، پیام به داورها، لحظه کلیدی، وضعیت داورها، جدول مخفی، مراسم اهدای جوایز؛
  و با روشن شدن امکان مربوط: اعتراض‌ها (VAR)، کارت شانس، بودجه، دورهای تصمیم‌گیری، جدول حذفی، رأی هم‌تیمی‌ها، ثبت‌نام‌ها.
- **تابلو:** تایمر و برنامه مراحل، نوار خبری، برند مشتری، گروه/کاپیتان/بهترین بازیکن/بودجه/نشان‌ها کنار نام تیم، مراسم جوایز،
  کارت شانس، و پنل‌های چرخشی نمودار روند، جدول حذفی و تصمیم تیم‌ها (کلیدهای T، B و D).
- **برگرداندن تغییرات:** تغییرات ثبت‌شده در «تاریخچه تغییرات» (۳۰ مورد آخر) قابل برگرداندن‌اند، مگر اینکه بعد از آن همان داده دوباره تغییر کرده باشد.
- **برگزارکننده‌ها:** سوپرادمین برای هر مؤسسه حساب می‌سازد؛ برگزارکننده با نام کاربری در همان صفحه سوپرادمین وارد می‌شود و فقط مسابقه‌های خودش را می‌بیند.
- **اطلاع‌رسانی:** نتایج مراحل، کارت شانس، نتیجه دور تصمیم، پایان مراسم و نتایج نهایی به ربات بله، ایتا، تلگرام یا یک وب‌هوک (مثلاً سرویس پیامک) فرستاده می‌شود.
